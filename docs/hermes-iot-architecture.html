Hermes IoT Architecture

Current working shape for the Echo Pyramid gateway: a full-duplex WebRTC edge on the left, a profile-scoped Hermes IoT sidecar in the middle, and Deepgram Flux/Aura speech services on the right. Hermes remains the agent brain over /v1/responses; the gateway owns transport, pairing, session mapping, and device state.

Ownership Split

  • • Echo Pyramid firmware handles audio I/O, playback, touch, LEDs, and reconnect behavior.
  • • The Hermes IoT gateway handles WebRTC, pairing, auth, session mapping, and device state.
  • • Hermes itself remains the source of truth for prompts, memory, skills, and tool use.

Live Speech Loop

  • • Upstream mic audio reaches the gateway over SRTP/WebRTC and is streamed into Deepgram Flux.
  • • Flux returns turn state and transcripts; the gateway forwards the user turn into Hermes /v1/responses.
  • • Hermes text is rendered by Aura and streamed back to the device over the outbound WebRTC audio track.

Packaging Reality

  • • Today this is a profile-native sidecar: it boots from HERMES_HOME and installs its plugin into the profile.
  • • The runtime boundary is already adapter-ready, but Hermes core does not yet load custom gateway adapters from packages.
  • • The simulator and real Pyramid share the same contract, so local validation stays close to hardware behavior.
